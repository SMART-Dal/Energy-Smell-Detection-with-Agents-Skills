## Common patterns

Work spent on every element of a collection when the result needs only some of them. Look for a full sort followed by an index or slice -- `sorted(xs)[0]` for a minimum, `sorted(xs, reverse=True)[:k]` for the top k -- an expensive test run over every value, repeats included, before a set keeps the distinct results, a transform applied before a filter that reads only the raw element, and rows selected in Python that a query could filter at the source. The expensive step is paid for elements that never reach the result.

### 1. the top k, without sorting everything
**Measured:** less energy on `k-tiny`; more on `k-most`, `edge`. **Decide which form fits.**
### 2. deduplicate before the per-element test
**Measured:** less energy on `dense-duplicates`; no change on `all-unique`. **Apply the after.**
### 3. materialising everything to take one item
**Measured:** less energy on `large`. **Apply the after.**
## Looks like it, but is not

### the first ten are not the top ten

```python
def _weight(row):
    return sum(ord(c) for c in row) % 9_973


def before(rows, k):
    return sorted((_weight(r) for r in rows), reverse=True)[:k]
```

The tempting repair:

```python
from itertools import islice


def _weight(row):
    return sum(ord(c) for c in row) % 9_973


def after(rows, k):
    return list(islice((_weight(r) for r in rows), k))
```

**Why not:** The consumer wants the largest k, which is a question about every element; `islice` returns the first k in input order, which is a different answer.

### the filter tests the transformed value

```python
scores = [expensive(x) for x in items]
best = [s for s in scores if s > threshold]
```

The tempting repair:

```python
best = [expensive(x) for x in items if x > threshold]
```

**Why not:** The predicate reads `expensive`'s output, so filtering first tests the raw item instead and keeps a different set; there is nothing to filter on until the transform has run.
######## C3.S7
## Common patterns

A loop that removes, inserts, reorders or appends to the collection it is scanning. Removing from a list shifts the rest down, so a `for` loop skips the next element, and every `remove`, `pop` or `del` in the loop moves the whole tail, so a filtering loop that deletes as it goes is quadratic where a rebuild is linear. Appending can run the loop without end, a new key in a dict being iterated raises `RuntimeError`, and a `while` loop whose counter is not updated on every path never ends.

### 1. removing from a list while scanning
**Measured:** less energy on `large`, `small`. **Apply the after.**
### 2. `del` inside a `while`, rebuilt instead
**Measured:** less energy on `many-removals`, `few-removals`. **Apply the after.**
## Looks like it, but is not

### rebinding is not rebuilding

```python
def before(batches):
    for values in batches:
        i = 0
        while i < len(values):
            if values[i] % 3 == 0:
                del values[i]
            else:
                i += 1
    return sum(len(v) for v in batches)
```

The tempting repair:

```python
def after(batches):
    for values in batches:
        values = [v for v in values if v % 3]     # rebinds the local only
    return sum(len(v) for v in batches)
```

**Why not:** Rebuilding with `values = [...]` rebinds a local and leaves every other reference to the list pointing at the unfiltered version; the rebuild has to keep the list's identity, with `values[:] =`, when anything else can see it.

### a work list that is meant to grow

```python
def work_list(pending):
    seen = []
    while pending:
        node = pending.pop()
        seen.append(node)
        pending.extend(node.children)
    return seen
```

The tempting repair:

```python
def work_list(pending):
    seen = []
    for node in list(pending):
        seen.append(node)
        pending.extend(node.children)
    return seen
```

**Why not:** Growing `pending` is how the traversal reaches the children; walking a snapshot visits only the nodes present at the start and never descends.

### one removal, then the loop stops

```python
def remove_then_stop(users, target):
    for user in users:
        if user is target:
            users.remove(user)
            break
```

The tempting repair:

```python
def remove_then_stop(users, target):
    users[:] = [user for user in users if user is not target]
```

**Why not:** The `break` ends the loop straight after the removal, so no element is skipped. The rebuild removes every occurrence of `target` where the original removes one.

## Common patterns

A boolean chain whose earlier operand does work -- a call, or a sub-expression that builds something -- while a later operand is a comparison, an attribute read, a `len` or a flag that could decide the result alone. `and` stops at the first false operand and `or` at the first true one, so with the cheap test second the expensive one runs on every evaluation, including those the cheap test would have settled. In a comprehension filter or a per-row condition, that is paid once per element.

### 1. the cheap test decides most inputs
**Measured:** less energy on `mostly-unpublished`; no change on `mostly-published`. **Apply the after.**
### 2. the expensive operand builds a set
**Measured:** less energy on `mostly-exhausted`; no change on `mostly-retrying`. **Apply the after.**
### 3. expensive test evaluated first
**Measured:** less energy on `cheap-test-rejects-most`; no change on `cheap-test-rejects-none`. **Apply the after.**
## Looks like it, but is not

### the cheap operand is the guard for the expensive one

```python
def _tier_rank(profile):
    return sum(ord(c) for c in profile["tier"]) % 7


def before(rows, wanted):
    return [r for r in rows if r["profile"] is not None and _tier_rank(r["profile"]) == wanted]
```

The tempting repair:

```python
def _tier_rank(profile):
    return sum(ord(c) for c in profile["tier"]) % 7


def after(rows, wanted):
    return [r for r in rows if _tier_rank(r["profile"]) == wanted and r["profile"] is not None]
```

**Why not:** `r["profile"] is not None` is the guard that makes the expensive operand safe to evaluate; swapped, the profile lookup runs on rows that have no profile and raises.

### `or` returns the first truthy operand, not just a boolean

```python
def get_author(post_id, fallback_user):
    return fetch_username(post_id) or fallback_user
```

The tempting repair:

```python
def get_author(post_id, fallback_user):
    return fallback_user or fetch_username(post_id)
```

**Why not:** `or` returns the value of the first truthy operand, so reordered, a truthy fallback is returned every time and the username is never fetched.

A condition whose answer is already fixed when it runs. ### 1. a test whose answer arithmetic already fixed
**Measured:** less energy on `mostly-below`, `mostly-above`. **Apply the after.**
### 2. a prior branch settles half the next condition
**Measured:** less energy on `last-only`; more on `neither`, `few-calls`. **Decide which form fits.**
### 3. an `elif` restating the negation of its `if`
**Measured:** less energy on `mixed-signs`; no change on `all-negative`. **Apply the after.**
### 4. the determined test stands in front of a whole scan
**Measured:** less energy on `k-positive`; no change on `k-negative`. **Apply the after.**
### 5. the same test nested inside itself
**Measured:** less energy on `large`, `small`. **Apply the after.**
## Looks like it, but is not

### the branch between the two tests is what changes the answer

```python
def before(items, ceiling):
    kept = 0
    for item in items:
        depth = item % 5
        if depth > 0:
            depth -= 1                    # the intervening modification
            if depth > 0:
                kept += ceiling
    return kept
```

The tempting repair:

```python
def after(items, ceiling):
    kept = 0
    for item in items:
        depth = item % 5
        if depth > 0:
            depth -= 1
            kept += ceiling               # "already established"
    return kept
```

**Why not:** The first branch decrements `depth` before the second test runs, so the two identical comparisons ask about different values; deleting the second keeps items the original rejected.

### the lock was released between the two tests

```python
with self._lock:
    if key in self._cache:
        return self._cache[key]
value = compute(key)
with self._lock:
    if key in self._cache:      # another thread may have filled it
        return self._cache[key]
    self._cache[key] = value
    return value
```

The tempting repair:

```python
with self._lock:
    if key in self._cache:
        return self._cache[key]

    self._cache[key] = value
    return value
```

**Why not:** Another thread may fill the entry while the lock is released for `compute`; without the second test this thread overwrites it, which is the race the re-check exists to prevent.

### constants that look distinct but compare equal

### the guard has to invent an answer the original raises on

```python
def median(values):
    ordered = sorted(values)
    return ordered[len(ordered) // 2]
```

## Looks like it, but is not

### the list is the answer, so its order is part of the result

```python

for row in rows:
    if row.id not in seen:
        seen.append(row.id)
```

## Looks like it, but is not

### a running total of strings

```python
def join_messages(messages):
    out = ""
    for msg in messages:
        out += msg
    return out
```

The tempting repair:

```python
def join_messages(messages):
    return sum(messages, "")
```

**Why not:** `sum` refuses strings: `sum(messages, "")` raises `TypeError` and its message says to use `''.join(seq)` instead. What an accumulator is comes from where it starts, not from what is added to it.

### two accumulations in one pass

```python
total = 0
largest = float("-inf")
for value in values:
    total += value
    if value > largest:
        largest = value
return total, largest
```

The tempting repair:

```python
return sum(values), max(values)
```

**Why not:** Two primitives make two passes where the loop made one. If `values` is a generator, `sum` consumes it and `max` then raises `ValueError` on an empty sequence.

## Looks like it, but is not

### `isinstance`, where subclasses must match

```python
for item in items:
    if isinstance(item, Widget):
        render(item)
```

The tempting repair:

```python
for item in items:
    if type(item) == Widget:
        render(item)
```

**Why not:** `type(item) == Widget` is a pointer comparison and rejects the subclasses `isinstance` accepts, so instances of a `Widget` subclass stop being rendered.

### parity on operands that may not be integers

```python
if n % 2:
    handle_odd(n)
```

The tempting repair:

```python
if n & 1:
    handle_odd(n)
```

**Why not:** `&` is defined only for integers: if `n` can be a float, `n & 1` raises `TypeError`, and for a type with its own `__mod__` the mask does not apply at all. The swap needs integer operands.

## Looks like it, but is not

### a body that also logs

```python
kept = []
for row in rows:
    if not row.valid:
        log.warning("dropping %s", row.id)
        continue
    kept.append(row)
return kept
```

The tempting repair:

```python
return [row for row in rows if row.valid]
```

**Why not:** The loop body also logs every row it drops. The comprehension keeps the same rows and loses the warnings.

### an early exit

```python
seen = []
for line in stream:
    seen.append(parse(line))
    if len(seen) >= limit:
        break
return seen
```

The tempting repair:

```python
return [parse(line) for line in stream][:limit]
```

**Why not:** The loop stops reading at `limit`. The comprehension parses and consumes the whole stream before slicing, so a long stream is read to the end and an endless one never returns.

### a list the caller passed in

```python
def populate_queue(shared_queue, new_items):
    for item in new_items:
        shared_queue.append(item.data)
```

The tempting repair:

```python
def populate_queue(shared_queue, new_items):
    shared_queue = [item.data for item in new_items]
```

**Why not:** The comprehension builds a fresh local list and rebinds the parameter, so the caller's list, which the loop was filling, stays empty. `shared_queue.extend(...)` keeps filling it.

### a filter that reads the list being built

```python
def reads_the_list_it_builds(xs):
    out = []
    for x in xs:
        if x not in out:
            out.append(x)
    return out
```

The tempting repair:

```python
def reads_the_list_it_builds(xs):
    out = []
    out = [x for x in xs if x not in out]
    return out
```

**Why not:** The loop's filter consults the list it is building. Inside the comprehension `out` is still the empty list, so every duplicate is kept.

## Common patterns

A string or bytes value grown once per iteration with `+=` or `s = s + part`: `self.buf += render_row(row)`, `grouped[key] += text`, `out += chunk` on a local. **Measured:** more energy on `three-parts`, `long-parts`. **Decide which form fits.**
## Looks like it, but is not

### the partial result is read inside the loop

```python
def render(self, rows):
    self.buf = ""
    for row in rows:
        self.buf += render_row(row)
        if len(self.buf) > self.limit:
            self.flush()
```

The tempting repair:

```python
def render(self, rows):
    parts = []
    for row in rows:
        parts.append(render_row(row))
        if len(self.buf) > self.limit:
            self.flush()
    self.buf = "".join(parts)
```

**Why not:** The partial result is read on every pass to decide when to flush. After a deferred join `self.buf` stays empty inside the loop and the flush never fires; a repair has to keep a buffer of parts flushed on a running length.
######## C11.S5
## Common patterns

Independent pieces of work run one after another when they could overlap: blocking waits -- network calls, sleeps, I/O -- each started only after the previous one returns, or independent CPU-bound tasks run in a single process. Serial work takes the sum of its parts where concurrent work takes the longest. During an I/O wait the process sits idle, so overlapping the waits removes idle time; CPU-bound Python gains nothing from threads, because the interpreter lock runs one at a time, and a process pool pickles every argument and result.

### 1. independent blocking waits run serially
**Measured:** less energy on `many-waits`; more on `one-wait`. **Decide which form fits.**
### 2. CPU-bound work across processes
**Measured:** more energy on `many-tasks`, `few-tasks`, `edge`. **Decide which form fits.**
### 3. threads for CPU-bound work
**Measured:** more energy on `many-tasks`, `one-task`, `edge`. **Decide which form fits.**
### 4. a whole matrix sent to every task of a process pool
**Measured:** more energy on `big-payload`, `small-payload`. **Decide which form fits.**
## Looks like it, but is not

### steps that must run in order

```python
for migration in migrations:
    apply(migration)
```

The tempting repair:

```python
with ThreadPoolExecutor() as pool:
    list(pool.map(apply, migrations))
```

**Why not:** Migration N assumes N-1 has run, and nothing in the loop says so. Run concurrently, the migrations apply out of order against a half-migrated schema.

### reads whose order is the result

```python
for step in trajectory:
    position = advance(position, step)
    samples.append(field[position])
```

The tempting repair:

```python
positions = []
for step in trajectory:
    position = advance(position, step)
    positions.append(position)
for position in sorted(positions):
    samples.append(field[position])
```

**Why not:** `samples` records the field along the path in the order it was walked; visiting the positions sorted appends the same values in a different order, which every reader of `samples` takes for a different path.
